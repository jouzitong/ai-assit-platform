# 后端配置规范

## 1. 目标

后端配置统一分为两类：

1. 启动配置：服务启动、Spring 容器初始化或基础设施装配时必须确定的配置。
2. 运行时配置：服务启动后仍可能调整，并由业务逻辑在运行过程中读取的服务级配置。

两类配置的存储位置和使用方式必须明确，不能因为“配置”这个名称相同，就混用
`application.yaml`、`application.properties` 和 `SystemSettingInternalApi`。

本规范约束的是服务级配置，不替代用户数据、业务数据和领域元数据的持久化设计。模型、
知识库等拥有独立业务实体和 CRUD 生命周期的数据，继续遵循对应领域规范；只有其中
属于服务级运行参数的部分，才按本规范使用系统参数。

## 2. 配置边界

| 配置类型 | 判断标准 | 存储方式 | 典型内容 | 生效方式 |
| --- | --- | --- | --- | --- |
| 启动配置 | 服务启动前或容器初始化时必须确定；缺失时服务不能正确启动 | 本地或云端管理的 `application.yaml` / `application.yml` / `application.properties` | 端口、数据源、注册中心、配置中心、日志、线程池基础参数、外部服务启动依赖 | 通常需要重启服务；是否支持刷新由基础设施能力明确约定 |
| 运行时配置 | 服务已启动后仍可调整；业务逻辑需要在运行时读取 | 系统参数存储，通过 `SystemSettingInternalApi` 读取 | Provider 地址和认证参数、默认数据源 key、知识库 ID、业务开关、限流阈值 | 按业务读取时生效，或由业务自行定义缓存和刷新策略 |

### 2.1 启动配置

启动配置必须使用 Spring Boot 标准配置文件承载：

- 本地开发、测试或单机部署使用项目约定的 `application.yaml`、`application.yml` 或
  `application.properties`。
- 云端部署可以由 Nacos 等配置中心托管，但配置内容仍遵循 Spring Boot
  `application.*` 的层级和绑定语义；不能另造一套仅供业务代码解析的配置协议。
- 使用 `@ConfigurationProperties` 绑定结构化配置；只有少量、明确的基础值才使用
  `@Value`。配置类应放在实际使用它的启动模块或基础设施模块中。
- 端口、数据源、注册发现、配置中心连接信息、日志基础配置、Bean 装配开关等都属于
  启动配置，不得迁移到系统参数后再通过业务代码补救启动流程。

启动配置可以由环境变量、容器 Secret 或云端配置中心注入敏感值，但这仍然是启动配置，
不因此变成运行时配置。启动配置的来源、优先级和敏感值注入方式应由部署规范另外说明。

### 2.2 运行时配置

运行时配置必须满足以下条件：

- 服务启动后可以被修改，且修改不应要求重新构建服务。
- 配置属于服务或系统级参数，而不是某个用户提交的业务数据。
- 配置值可以被序列化为系统参数的字符串值，并能在读取方完成明确的类型转换和校验。
- 配置缺失、禁用或格式错误时，读取方有清晰的失败语义或已文档化的默认值。

满足上述条件的服务级运行时配置，统一存储在系统参数中，并通过
`SystemSettingInternalApi` 读取。业务代码不得直接访问系统参数表、直接依赖
`SystemSettingMapper`，也不得把同一个 key 同时复制到本地配置文件和系统参数中。

以下内容不应伪装成运行时配置放入系统参数：

- 用户、租户、角色等业务数据；
- 需要复杂查询、关联关系、独立权限或完整版本管理的领域实体；
- 大型文档、列表数据和历史快照；
- 每次请求或每个会话都不同的临时上下文。

这些数据应使用所属领域的数据表、请求参数或上下文对象承载。系统参数只保存服务级
配置本身，避免演变成无结构的业务数据库。

## 3. 配置类型判定规则

新增配置时按以下顺序判断：

1. 如果配置影响服务监听、组件创建、连接池、注册发现、配置中心或 Spring Bean 装配，
   定义为启动配置，放入 `application.*`。
2. 如果服务启动后需要由管理端调整，且调整不应依赖重启，定义为运行时配置，放入系统
   参数并通过 `SystemSettingInternalApi` 读取。
3. 如果配置实际描述的是可独立管理的业务对象，使用该业务对象自己的表和服务，不因
   “可配置”而强行放入系统参数。
4. 如果同一配置同时影响启动和运行时，拆成两个明确配置：启动阶段所需的基础配置放入
   `application.*`，业务运行阶段可调整的参数放入系统参数，并分别命名。

不要使用“先放系统参数，启动时再查询”的方式承载启动配置。启动阶段依赖数据库、远程
服务或业务 API，会使配置加载与服务可用性互相依赖，也会增加启动失败的排查成本。

## 4. `SystemSettingInternalApi` 使用规范

当前内部读取契约是按 key 查询字符串值：

```java
R<String> queryValueByKey(@RequestParam("key") String key);
```

调用方必须遵循以下约束：

- key 必须引用本模块定义的常量，不允许在业务方法中散落硬编码字符串。
- 通过 `SystemSettingInternalApi` 获取值后，立即在配置解析边界完成非空校验、类型转换和
  格式校验；不要把原始字符串继续传递到多个业务层再分别解析。
- `response` 为空、返回失败、配置不存在、配置被禁用或值为空时，按配置定义处理；必填
  配置必须抛出可定位的业务异常，不能静默返回 `null`。
- 只有在 key 文档明确声明了默认值时，才允许使用默认值；默认值也必须与文档和代码保持
  一致。
- 不要使用 `@Value` 或 `@ConfigurationProperties` 读取运行时系统参数，也不要在启动时把
  运行时参数复制为单例字段，除非同时实现明确的刷新机制。
- 如果业务需要缓存运行时配置，必须在代码和 key 文档中说明缓存范围、过期时间、刷新方式
  和更新后的最晚生效时间。

系统参数的写入应通过系统参数管理能力完成；调用方只依赖内部 API 读取，不直接操作系统
参数表或 Mapper。当前 `SystemSettingInternalApi` 是内部读取契约，不应直接暴露为前端管理
接口。

## 5. Key 常量规范

每个运行时配置 key 必须在其归属业务模块中定义常量。新 key 推荐使用服务、领域和用途
组成的点分格式，例如 `chat.engine.kb.client.list`。已经使用的 key 不要仅为了统一命名
而直接修改；如需迁移，应保留兼容读取和明确的废弃计划。

常量名应表达用途，推荐使用 `<PURPOSE>_SETTING_KEY` 或包含领域前缀的等价命名；禁止使用
多个含义不清的 `KEY`、`CONFIG` 常量覆盖不同系统参数。

常量的 Javadoc 必须同时说明以下信息：

- 用途：这个 key 控制什么行为，由哪个模块使用；
- 类型：`STRING`、`INTEGER`、`DECIMAL`、`BOOLEAN`、`JSON_OBJECT` 或 `JSON_ARRAY` 等；
- 具体数据格式：字符串约束、数值单位和范围，或 JSON 的字段、字段类型和必填关系；
- 是否必填以及缺失时的默认行为；
- 是否包含敏感信息，日志和管理端展示如何脱敏；
- 生效方式：实时读取、缓存读取、定时刷新还是需要重启；
- 兼容要求：历史格式、迁移方式或废弃时间（如果存在）。

示例：

```java
/**
 * 知识库客户端列表。
 *
 * <p>用途：提供 Chat 运行时调用知识库 Provider 所需的地址和认证信息。</p>
 * <p>类型：JSON_ARRAY。</p>
 * <p>格式：数组元素必须包含 key、type、url；auth 为认证对象，type 为 bearer 时使用
 * value，type 为 aliyun_aksk 时使用 accessKeyId 和 accessKeySecret。</p>
 * <p>要求：当前业务必须且只能配置一个客户端；缺失或格式错误时拒绝调用。</p>
 * <p>敏感性：auth 中的认证值属于敏感信息，禁止写入日志和普通接口响应。</p>
 * <p>生效：由 Chat 运行时读取，具体缓存和刷新策略以调用服务实现为准。</p>
 */
public static final String KNOWLEDGE_CLIENT_LIST_SETTING_KEY =
        "chat.engine.kb.client.list";
```

## 6. 值类型和数据格式

系统参数表的 `settingValue` 是文本值，`valueType` 用于描述文本的业务类型。写入和读取
必须遵守以下规则：

- `STRING`：保存原始字符串；明确是否允许空白、大小写和长度上限。
- `INTEGER`：保存十进制整数；明确单位、最小值和最大值。
- `DECIMAL`：保存十进制定点数；明确精度、舍入方式和单位，不使用依赖本地化格式的字符串。
- `BOOLEAN`：统一使用 `true` 或 `false`，不混用 `1`、`0`、`yes` 等未约定值。
- `JSON_OBJECT` / `JSON_ARRAY`：保存标准 JSON；由 `ObjectMapper` 等统一解析，并对根类型、
  字段类型、必填字段和未知字段策略进行校验。

复杂 JSON 不得只在 description 中写一句“JSON 配置”。必须在 key 常量 Javadoc 或该配置
专题文档中给出最小示例和字段说明。修改 JSON 格式时，应优先增加兼容解析，再安排历史
数据迁移，不能只修改文档或只修改解析代码的一侧。

## 7. 安全、日志和变更

- API Key、Token、密码、密钥等值即使保存在运行时系统参数中，也必须按敏感配置处理。
- 日志只能记录 key、是否存在、解析结果摘要或脱敏后的值，禁止记录原始 `settingValue`。
- 管理端展示和查询接口只返回脱敏摘要；内部 Provider 调用使用原始值时，也不得把认证
  对象放入普通日志、异常消息或可持久化的业务快照。
- key 是稳定契约，不得在无兼容措施的情况下重命名、改变类型或改变 JSON 语义。
- 修改配置格式、必填字段、默认值或生效方式时，必须同步更新 key 常量 Javadoc、专题文档、
  解析校验和示例数据。

## 8. 提交前检查清单

- [ ] 已判断配置属于启动配置、运行时配置还是领域业务数据。
- [ ] 启动配置只出现在本地或云端管理的 `application.*` 中。
- [ ] 服务级运行时配置通过 `SystemSettingInternalApi` 读取，没有直接访问表或 Mapper。
- [ ] key 已定义为归属模块的常量，业务代码没有散落硬编码 key。
- [ ] key 常量已说明用途、类型、具体格式、必填/默认值、敏感性和生效方式。
- [ ] 读取边界已完成响应状态判断、非空校验、类型转换和格式校验。
- [ ] 缺失、禁用、格式错误和 Provider 调用失败的行为已明确。
- [ ] 日志、异常和管理端输出没有泄露敏感配置。
- [ ] 若有缓存或刷新机制，已写明生效时限并完成对应验证。
