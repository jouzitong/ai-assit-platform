# 后端日志规范

## 1. 目标

- 统一后端业务日志的打印标准，保证问题出现后能追溯、能排障、能审计。
- 统一不同日志级别的使用边界，避免把正常信息打成错误，或把真正异常淹没在低级别日志里。
- 约束日志内容和上下文，避免只打印一句“执行失败”却没有定位线索。

## 2. 基本原则

- 日志首先服务于排障，其次服务于审计和运行观察，不是为了“多打一点更安全”。
- 每条业务关键日志都应尽量回答三个问题：谁操作、操作了什么、结果是什么。
- 日志要可串联同一次请求、同一次任务、同一次外部调用链，避免单点日志无法还原上下文。
- 正常分支按事实打印，不要把业务预期内的失败全部打成 `error`。
- 同一异常不要在多层重复打印完整堆栈，避免噪音和误判。

## 3. 可追溯与审计要求

### 3.1 基础追踪字段

- 请求链路日志默认要能关联 `traceId`。
- Web 场景优先复用请求头 `X-Trace-Id`；如果上游未传，使用系统生成并写入 MDC 的 `traceId`。
- 异步任务、消息消费、定时任务、批处理等非 Web 场景，也要显式补齐可追踪的链路标识，例如：
  - `traceId`
  - `taskId`
  - `jobId`
  - `messageId`

### 3.2 审计信息要求

- 涉及新增、修改、删除、发布、绑定、审批、导入、导出等操作时，日志至少要包含：
  - 操作人：`userId`、`operator`
  - 操作对象：业务类型、主键 `id`、必要时补充业务编码
  - 操作动作：做了什么
  - 操作结果：成功 / 失败
- 如果是跨系统操作，补充目标系统、目标资源标识、调用结果码。
- 如果是状态流转，补充关键状态变化，例如 `fromStatus`、`toStatus`。

### 3.3 敏感信息约束

- 日志中禁止直接打印密码、token、密钥、完整 cookie、完整证件号、完整手机号、完整邮箱、原始个人隐私数据。
- 必须打印时只保留必要片段，其他内容脱敏。
- 不要把完整请求体、完整响应体作为默认日志行为；只有明确排障需要且确认无敏感数据时，才允许按需打印。

## 4. 日志级别规范

### 4.1 `INFO`

- 更新类操作默认使用 `info`，包括新增、修改、删除、发布、上下线、审批、绑定解绑等。
- 关键流程节点成功落地时使用 `info`，前提是这些节点对业务排障和审计有价值。
- 启停、配置加载、关键外部依赖初始化成功等运行阶段事件可使用 `info`。
- 不要把高频普通查询全打成 `info`，否则会稀释真正重要的业务操作日志。

### 4.2 `DEBUG` / `TRACE`

- 查询类日志、过程型明细日志、分支命中日志、入参与中间结果，使用 `debug` 或 `trace`。
- 一般业务查询记录优先使用 `debug`。
- 高频、超细粒度、只在深度排障时才有价值的内容使用 `trace`。
- 打印查询结果时只保留必要摘要，不要默认整对象、整列表直接输出。

### 4.3 `WARN`

- 已知、可预测、可控的异常或失败使用 `warn`。
- 典型场景包括：
  - 业务预期内校验失败
  - 外部依赖短暂失败但系统已降级处理
  - 重复请求、幂等拦截、资源不存在、状态不满足
  - 非法入参、权限不足、配额不足等已知业务分支
- `warn` 重点是把原因讲清楚，而不是只写“操作失败”。

### 4.4 `ERROR`

- 未知、不可控、需要人工介入或后续重点排查的异常使用 `error`。
- 典型场景包括：
  - 未预期的运行时异常
  - 数据损坏、状态错乱、关键数据丢失风险
  - 外部系统长时间不可用且无法降级
  - 理论上不应该进入的分支
- `error` 默认应附带异常堆栈或原始 `cause`，保证事后排查有足够上下文。

## 5. 内容规范

- 日志文案要直接表达事实，避免“这里出问题了”“执行异常”这类空泛描述。
- 日志至少应包含当前业务主体的关键标识，例如：`sessionId`、`workflowId`、`kbId`、`documentId`、`datasourceId`。
- 对修改类操作，优先打印“改了哪个对象、哪个关键字段、结果如何”，不要无差别打印整份 before/after 大对象。
- 对批量操作，打印总量、成功数、失败数、失败原因摘要；不要把每条明细都打在同一级别的主日志里。
- 对外部调用，至少打印目标系统、接口/动作、耗时、结果码；需要时再在 `debug/trace` 下补调用明细。

## 6. 异常与日志协同

- 抛出异常前，先判断该异常是否会在上层统一记录；若会，不要当前层和上层同时打印同一份堆栈。
- `BizException`、参数错误、已知业务拒绝等可预期异常，默认按 `warn` 记录，不作为系统故障打 `error`。
- 未知异常、框架异常、底层依赖异常、数据一致性异常按 `error` 记录，并保留原始堆栈。
- 只记录异常 message 不记录 `cause` 的做法视为不合格日志。

## 7. 常见反模式

- 查询接口每次都打 `info`，导致日志量膨胀。
- 已知业务失败直接打 `error`，造成告警噪音。
- 发生异常时只打印“失败”二字，没有对象标识、没有上下文、没有异常栈。
- 在 controller、service、client 三层重复打印同一异常栈。
- 为了省事直接 `log.info("{}", dto)`，把大对象、敏感字段全部打出去。

## 8. 落地建议

- 新增业务操作时，先补关键 `info` 审计日志，再按需要补 `debug/trace` 过程日志。
- 打日志时优先使用稳定键值表达上下文，避免纯自然语言难以检索。
- 关键链路统一贯穿 `traceId`，保证 Web、异步任务、消息消费的日志都能串起来。
- 如果一个场景后续要做审计、对账或问题复盘，宁可补结构化关键信息，也不要依赖模糊文案回忆现场。
